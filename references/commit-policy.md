# Git 提交专项规则

## 提交格式

- `[MUST]` 使用 Conventional Commits（如 `feat:`、`fix:`、`chore:`、`refactor:`、`docs:`）。
- `[DEFAULT]` 使用 Conventional Commits 且改动范围清晰时，可按需添加 scope，如 `feat(file-approval): ...`、`fix(api): ...`；scope 应使用项目既有模块名、业务域名或目录名，不为单文件小改动强行添加。
- `[MUST]` 提交信息正文使用中文。
- `[MUST]` Git 提交标题后必须保留一个空行，再写正文。
- `[DEFAULT]` 提交正文默认使用中文短列表格式，每个改动点单独成行，以 `- ` 开头；正文 bullet 之间紧密相邻，不插入空行。
- `[MUST]` 每条正文只表达一个明确改动点，优先描述“做了什么”，不写冗长背景、推导过程或低信息量解释。
- `[DEFAULT]` 正文条目顺序优先为：主要功能或用户可见变化 -> 配套实现或数据结构/API 改动 -> 修复项或同步更新项。
- `[DEFAULT]` 常规提交正文建议为 2 到 5 条；改动较大时可适度增加，但仍保持“每行一个事实”的短列表结构。
- `[DEFAULT]` 正文常用表述保持直接、结果导向的动词起句，例如：`新增...`、`修复...`、`改为...`、`增加...`、`移除...`、`同步更新...`、`从...改为...`。
- `[MUST NOT]` 不得将多个无关改动塞入同一条正文中，不得使用大段自然段替代短列表，也不得仅写动机而不写具体改动内容。
- `[DEFAULT]` 当提交内容属于单一主题且需要一句总述时，可在正文首行写一条总述，再继续使用短列表；但默认仍以纯短列表为主。
- `[DEFAULT]` 仅当提交内容天然具有步骤性、映射关系或分阶段结构时，才允许使用编号列表（如 `1. 2. 3.`）；未命中该场景时，优先使用 `- ` 列表。

## 多行正文与命令行提交

- `[MUST]` 生成 Git 提交信息时，正文若为多行，必须使用真实换行，不得输出字面量 `\n`。
- `[MUST NOT]` 不得将多行提交正文压成单个字符串并包含转义序列 `\n`、`\r\n` 或其他可见转义文本。
- `[MUST NOT]` 不得使用会导致每条正文之间自动插入空白段落的提交方式（如将每个 bullet 分别作为独立 `-m` 正文段落），正文 bullet 之间也不得手动插入空行。
- `[DEFAULT]` 需要多行提交信息时，优先生成一行标题、一个空行、1 到 3 行中文正文。
- `[DEFAULT]` 若命令行执行提交，优先使用两个 `-m` 参数：第一个只放标题，第二个放完整正文；正文中的多条 bullet 必须放在同一个 `-m` 参数内并使用真实换行。
- `[MUST]` 使用 `git commit -m` 且正文包含 2 条及以上 bullet 时，最多只允许两个 `-m` 参数：标题一个、完整正文一个；不得使用 3 个或更多 `-m` 参数拆分正文 bullet。
- `[DEFAULT]` 多行正文也可使用提交信息文件并通过 `git commit -F <file>` 提交；提交信息文件内容必须使用真实换行。

## 推荐模板

```text
<type>: <标题>

- 主要改动点 1
- 主要改动点 2
- 配套实现或结构调整
- 修复项或同步更新项
```

## 提交边界

- `[MUST]` 仅提交与当前任务直接相关的文件。
- `[MUST]` 发现无关改动时，不纳入本次提交并在交付中说明。
